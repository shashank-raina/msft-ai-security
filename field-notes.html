Learned the hard way

Field
notes

Everything else on this site you could, eventually, assemble from Microsoft's documentation. This page you couldn't. These are the things that bit me — or nearly did — while actually deploying this stack: schema traps, licence boundaries dressed up as empty tables, and controls that stopped working without saying so. Short, specific, and dated August–September 2026.

NOTE 01

A bare arg_max(Timestamp, *) collapses your fleet to one row

AgentsInfo stores repeated snapshots of every agent, so the tempting one-liner summarize arg_max(Timestamp, *) returns exactly one agent — the most recently written row in the entire table. I shipped that into a workbook tile and stared at an inventory of one for longer than I'd like to admit. The correct reduction is summarize arg_max(Timestamp, *) by AgentId, and then filter out LifecycleStatus == "Deleted", or your inventory quietly counts ghosts.

NOTE 02

An empty table means one of three things

Before declaring a data gap, work out which one: the licence gate isn't met, you're on the wrong query surface, or there is genuinely no data. The surfaces don't degrade gracefully — a table queried on the wrong one fails outright. CopilotActivity is a Log Analytics table that Advanced Hunting has never heard of; UnifiedAgentObservability exists only in the Sentinel data lake; AgentsInfo populates its local-agent rows on E5 but needs Agent 365 for the cloud ones. Same symptom, three different fixes — and only one of them costs money.

NOTE 03

Legacy Copilot Studio agents have no identity to govern

Agents built before agent identities existed authenticate with an ordinary app registration or the maker's own credentials. Entra's Agent ID blade and the lake identity tables both draw a blank on them — and that invisibility is precisely what makes them the population to worry about. The service principal tag AgentCreatedBy:CopilotStudio is how I find them. The Agent Registry tells the opposite story: it happily lists these classic agents — alongside entries synced in from Power Platform and Dynamics 365 that are barely agents at all. So the registry overcounts while the identity views undercount, and neither number is the estate. If your governance story starts at "agents with identities", these agents aren't in it.

NOTE 04

The documentation and the deployed schema disagree on names

The retired AIAgentsInfo still sits in the schema listing next to its replacement, months past its own cut-off date. Earlier this year Learn pages called the new table AgentInfo while the portal deployed AgentsInfo, and rendered the Graph audit table with two different spellings — both since fixed, quietly, which is rather the point. The docs and the schema drift apart and back together without announcements, so the schema tab in your own portal outranks any web page, this one included.

NOTE 05

Some tables ship before their schemas do

The four EntraAgent* identity tables landed in the data lake (preview) with no published column reference — the announcement blog shows a handful of camelCase fields, and that's all anyone has. Every query I write against them wraps columns in column_ifexists() and carries a "validate in-tenant" flag. Preview tables are absolutely usable; just never let a dashboard break because a column got renamed underneath it.

NOTE 06

Nobody agrees how many agents you have

The registry counts published titles. Defender's inventory counts what it can see, local agents included. Entra counts only what holds a directory principal. Even within one product, Microsoft's own documentation shows the registry portal tile and the catalog API returning different counts for the same tenant. The spread between these numbers is usually the finding itself. How I reconcile them is on the Agent Map page.

NOTE 07

Observability and identity are independent — never infer one from the other

The Agent 365 SDK's capabilities are separable, and its observability can run on a plain Entra app registration. So an agent can send you rich telemetry while holding no agent identity at all, and an agent with a first-class identity can be telemetry-silent. I audit them as two columns, and the interesting rows are the ones where they disagree.

NOTE 08

The blueprint holds the credentials — and the blast radius

Agent identities hold no credentials of their own — the blueprint holds the secrets and impersonates its agents. One leaked blueprint credential is therefore every agent under that blueprint; Microsoft's own guidance calls blueprint count "a security boundary decision". The useful corollary: disabling a blueprint stops all of its agents authenticating, in one action. That's your fleet kill switch. Write it into the emergency runbook before you need it.

NOTE 09

Controls don't always survive platform migrations

When agent blocking moved under the Security for AI policy umbrella in mid-2026, pre-existing Block rules were reported to simply stop enforcing until recreated in the new location — no error, no alert, just an old rule that no longer did anything. Verify that one in your own tenant; it's exactly the kind of behaviour that gets fixed quietly. The durable lesson stands either way: after every platform migration, ask which of your controls came along — and how you would know.

NOTE 10

"We block paste into AI" rarely means what people think

Defender for Cloud Apps session controls apply only to apps onboarded to Conditional Access App Control — which public AI sites are not, so a session policy never sees that paste. Endpoint DLP can govern it, but paste content is classified locally: exact data match and trainable classifiers don't fire on paste; only standard pattern-based sensitive info types do. And blocking carries its own cost — people route around controls, so visibility is usually worth more than prohibition.

NOTE 11

Entra's "Copilot Studio" label tells you which machinery minted the identity

Every Copilot Studio app-based agent identity in Entra is a child of one shared global blueprint — and that population is bigger than the agents anyone built in the Studio. Agent flows (Power Automate) receive Entra Agent IDs through the same integration, and first-party product agents provisioned through the Power Platform machinery are reported to land there too — that last part I haven't found written down, so verify it in your tenant. Two consequences. Counting the blueprint's children as "Copilot Studio agents someone built" overcounts. And the sharper one: a Conditional Access policy or a disable aimed at that blueprint hits everything under it — flows and product-provisioned agents included. Blueprint-level actions are population-level actions.

These notes date fast — that's rather the point. Anything here older than a couple of months deserves re-verification against Microsoft Learn before you rely on it.
